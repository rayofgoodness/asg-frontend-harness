# task-harness: гід для команди

Плагін для Claude Code. Даєш номер задачі з YouTrack — отримуєш гілку з одним комітом, перевірену гейтами й трьома ревʼюерами, і готовий до відкриття MR. Push і MR харнес робить тільки після твого «так».

Цей гід про те, як поставити й користуватись. Як усе влаштовано всередині — у [README.md](README.md).

## 1. Що потрібно

| | macOS | Windows |
|---|---|---|
| Claude Code | так | так |
| Git | так | Git for Windows (разом з Git Bash) |
| Node.js 18+ | так | так |
| `glab` з авторизацією | так | так |
| YouTrack MCP у Claude Code | так | так |

Скрипти харнеса написані на Node, тому bash, WSL чи щось іще ставити не треба.

Перевір перед першим запуском:

```bash
node -v
```

```bash
glab auth status
```

У Claude Code команда `/mcp` має показувати YouTrack як підключений. Якщо його нема, харнес зупиниться на першому кроці й скаже про це.

## 2. Встановлення

У Claude Code:

```
/plugin marketplace add git@github.com:rayofgoodness/asg-frontend-harness.git
/plugin install task-harness@local-harness
```

Репозиторій приватний: потрібен доступ до нього і SSH-ключ для GitHub.

Оновлення до нової версії:

```
/plugin marketplace update local-harness
/plugin install task-harness@local-harness
```

Після встановлення чи оновлення перезапусти Claude Code.

## 3. Підготовка проєкту (один раз)

1. **Залежності встановлені.** `npm i` у проєкті пройшов, для Nuxt є папка `.nuxt` (її створює `npm i` через `nuxt prepare`). Під час задачі харнес блокує встановлення залежностей, тому зроби це заздалегідь.
2. **Робоче дерево чисте.** Закоміть або сховай свої зміни: з незакоміченими змінами харнес не стартує.
3. **Dev-сервер зупинений** на час задачі. Збірка в гейтах пише в ті самі `.nuxt` і `.output`; на Windows це закінчується помилкою блокування файлів.
4. **Правила команди лежать у проєкті.** Харнес читає `CLAUDE.md`, `.claude/rules/*`, `CONTRIBUTING.md` і ставить їх вище за власні дефолти. Якщо цих файлів у тебе локально нема, він піде на дефолтах: гілка `AMM-123`, коміт `AMM-123 Short description`, база `develop`.

`.gitignore` чіпати не треба: робочу папку `.harness/` харнес сам додає в локальний `.git/info/exclude`.

## 4. Запуск

Відкрий Claude Code у корені проєкту:

```
/task-harness:task AMM-123
```

Можна дати повне посилання на задачу замість номера.

| Прапорець | Що робить |
|---|---|
| `--plan-only` | зупиняється після плану, код не чіпає |
| `--auto` | не питає підтвердження плану; push і MR питає все одно |
| `--no-pr` | зупиняється після ревʼю, без push і MR |
| `--base <гілка>` | інша базова гілка замість `develop` |

Для першого разу бери `--plan-only`: побачиш, як харнес зрозумів задачу, нічим не ризикуючи.

## 5. Що відбувається і де тебе спитають

| Крок | Що робить харнес | Твоя участь |
|---|---|---|
| Задача | читає задачу, коментарі, звʼязки з YouTrack | — |
| Розбір | виділяє критерії приймання (AC) і неясності | відповісти на питання, якщо задача неоднозначна |
| Оцінка | оцінює складність і ризик, вибирає моделі | якщо задача завелика — отримаєш пропозицію розбити й зупинку |
| Аналіз | шукає в коді, що і де міняти | відповісти на відкриті питання, якщо є |
| План | ділить на 1–5 підзадач з файлами | **підтвердити, поправити або зупинити** |
| Виконання | робить підзадачі по одній, кожна — окремий коміт у гілці задачі | — |
| Гейти | eslint по змінених файлах, typecheck, тести, build | — |
| Ревʼю | три ревʼюери: обсяг, конвенції, коректність | — |
| Фікси | до двох кіл виправлень за зауваженнями | — |
| Здача | зводить коміти в один | **дозволити push**, потім **окремо дозволити MR** |

Найважливіше місце — план. Прочитай список файлів і розділ «Out of scope»: усе, чого там нема, зроблено не буде, а зайве ревʼюер обсягу потім зажадає прибрати.

## 6. Що харнес гарантує

- **Не пушить і не відкриває MR без прямого «так»** на питання саме про цю дію. `--auto` цього не скасовує.
- **Не чіпає `develop` і `master`**, не робить force-push, `reset --hard`, `rebase`.
- **Міняє тільки файли задачі.** Кожен зайвий файл має бути пояснений у звіті підзадачі, інакше зміна відкочується.
- **Лінтери й форматери — тільки ті, якими проєкт користується, і тільки на файлах задачі.** Нема в проєкті prettier — він не запускається і не завантажується. `eslint --fix` на файлі зі старими помилками заборонений, бо переформатував би чужі рядки.
- **Старі помилки eslint не твої.** Гейт падає лише на помилках, які внесла гілка; ті, що вже були у файлі, рахуються й ігноруються.
- **Не ставить і не оновлює залежності.**
- **Новий код пишеться з guard clauses.** Перевірки на початку функції з негайним `return`, без `else` після `return`, вкладеність не глибше 2. Ревʼюер конвенцій це перевіряє на доданих і змінених рядках; старий код заради цього не переписується.

Ці обмеження тримає хук (guard), а не тільки інструкції: заборонена команда просто не виконається. Діє він лише в тій сесії Claude Code, яка запустила задачу; в інших вікнах працюєш як завжди.

## 7. Якщо щось пішло не так

**Харнес зупинився і питає.** Це штатно: відповідай. Він зупиняється, коли неясна задача, знайдено чужі незакомічені зміни, підзадача заблокована або гейт упав через оточення.

**Сесія обірвалась або ти закрив Claude Code.** Запусти ту саму команду з тим самим номером: харнес продовжить з кроку, на якому зупинився.

**Хочеш перервати задачу.** Напиши в сесії «зупини задачу і зніми блокування». Якщо сесії вже нема, видали файл `.harness/ACTIVE` у корені проєкту. Блокування також знімається само через 24 години. Гілка задачі й папка `.harness/<ID>/` лишаються, нічого не губиться.

**«task-harness: … blocked».** Guard не пустив команду. У повідомленні сказано, яку і чому. Якщо задача вже не активна, а блокування лишилось — видали `.harness/ACTIVE`.

**Гейт упав з `INFRA:`.** Проблема в оточенні, а не в коді: нема `node_modules`, не стартує eslint. Полагодь оточення (`npm i`) і скажи харнесу продовжити.

**Гейт `js:build` упав на заблокованих файлах.** Працює dev-сервер. Зупини його і скажи продовжити.

**У звіті `SKIP js:typecheck` чи інші `SKIP`.** Перевірки нема в проєкті, це не помилка. Але памʼятай: чого не перевірив гейт, те перевіряєш ти.

**Харнес зробив не те.** Гілка локальна й не запушена: скажи, що не так, або видали гілку й запусти знову з уточненням у задачі. Якщо причина в неясному описі — краще поправити задачу в YouTrack.

## 8. Після харнеса

Харнес не замінює твою перевірку. Перед тим як дозволити push:

1. Подивись диф: `git diff develop...HEAD`.
2. Відкрий сторінку в браузері й пройди сценарій із задачі. Автоматичної перевірки в браузері в харнесі ще нема.
3. Прочитай `.harness/<ID>/summary.md`: що зроблено, які гейти пропущені, які зауваження ревʼюерів лишились.

Усі проміжні файли лежать у `.harness/<ID>/` і в git не потрапляють:

| Файл | Що в ньому |
|---|---|
| `issue.md` | задача, як її прочитав харнес |
| `plan.md` | план і «Out of scope» |
| `reports/` | звіт кожної підзадачі |
| `gates.txt`, `logs/` | результати гейтів і повні логи тих, що впали |
| `reviews/summary.md` | зведені зауваження ревʼюерів |
| `summary.md` | підсумок для MR |

## 9. Налаштування під проєкт

Усе необовʼязкове.

- **Правила коду й git** — у `CLAUDE.md` або `.claude/rules/*.md` проєкту. Це найдієвіший спосіб навчити харнес писати «як у нас».
- **Вимкнути гейт** — змінна `HARNESS_SKIP` у `.claude/settings.local.json`:

  ```json
  { "env": { "HARNESS_SKIP": "js:build" } }
  ```

  Вимкнені гейти потрапляють в опис MR як неперевірені.
- **Правила ризику** — файл `.harness-risk.json` у корені проєкту; формат у [README.md](README.md).

## 10. Питання й помилки

Знайшов баг у харнесі чи маєш ідею — заведи issue в репозиторії `rayofgoodness/asg-frontend-harness` і додай папку `.harness/<ID>/` з того запуску (без секретів): за нею видно, на якому кроці й чому пішло не так.
